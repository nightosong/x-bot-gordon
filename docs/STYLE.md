# Gordon 界面与交互风格约束

## 1. 目标

这份文档用于约束 Gordon 的桌面端设计风格，避免新功能开发时页面结构、交互方式和信息密度过度发散。

适用范围：

- `apps/desktop` 下的所有新页面和已有页面迭代
- 特别适用于“列表页 + 详情页 / 编辑页”类型的工作台页面

核心原则：

- 保持统一，但不再追求所有页面完全同构
- 主舞台优先于模板优先
- 操作路径清晰优先于形式整齐
- 允许更自由的视觉编排，只要主次关系仍然清楚

## 2. 整体视觉原则

### 2.1 信息密度

- 页面应保持克制，不要堆叠过多说明文字
- 说明信息优先内隐，不要大段外显提示
- 非必要说明尽量删除，只保留用户完成任务必须看到的信息
- 一个区域应有清晰主目标，但允许承担“信息 + 操作 + 状态”这三者中的紧密组合
- 不要为了“解释页面在做什么”而额外堆说明段落；标题、标签、布局已能表达的内容，不再重复写成文案块
- 工作台默认采用适度紧凑的信息密度：列表项、折叠块、编辑卡片和表单行优先使用 8-12px 级内边距与 6-10px 间距；高频折叠编辑器可进一步收紧到 4-8px 内边距与 4-8px 间距；只有页面级标题、空态和重点主舞台可以使用更大的留白
- 新增局部容器时，优先先检查是否能通过小字号状态、图标按钮、折叠区和紧凑行高完成表达，避免卡片内部出现大面积无功能空白
- 字段级 AI、快捷润色、局部生成这类上下文辅助入口应优先做成贴近字段的图标按钮；展开后使用紧凑悬浮面板承载指令、结果预览和写回动作，不升级为大面积说明卡或独立页面

### 2.2 视觉层级

- 页面级身份表达可以由顶部标题区、左侧导航摘要或当前主舞台共同承接
- 内容区应围绕一个 dominant canvas（主舞台）组织，允许搭配较轻的侧向信息轨道
- 标题、内容、操作三者要明确分层，但不要求永远切成固定的上下两段
- 编辑态页面优先聚焦内容本身，但允许保留与当前任务强相关的局部上下文模块

### 2.4 视觉语言

Gordon 当前统一采用 **Gordon Dark Glass Workbench（深色玻璃工作台）** 方向。

该方向只约束视觉语言，不改变已经确认的页面架构与排版：

- 保留“左侧品牌卡 + 左侧功能入口 + 右侧单一主工作区”的桌面壳层
- 保留列表态、编辑态、对话态之间已经确认的切换规则
- 保留功能进入独立工作区后吃满主容器的主舞台原则
- 视觉统一优先通过 token（设计变量）、卡片表面、状态色和控件质感完成，不为了统一而重排页面

核心视觉关键词：

- 深色基底：沿用当前海军蓝 / 深蓝黑工作台背景，不切换为浅色基底
- 青绿色主强调：用于主动作、激活态、成功态和可执行能力
- 暖金色辅助强调：用于品牌点缀、提示和局部高亮信息
- 珊瑚色风险强调：用于风险、删除、失败和需要提醒的状态
- 暗色玻璃卡片：统一主容器、列表卡、信息卡和编辑卡的边界语言
- 克制渐变：只用于背景光斑、主按钮、激活态和局部品牌表达
- 轻量轨道感：服务 Agent、任务流、workflow 等语义，避免高饱和重霓虹

- 默认沿用当前深色 Gordon 色系，不引入格格不入的浅色页面基底
- 使用明确的颜色方向，例如深蓝背景、青绿色主强调、暖金色辅助强调和珊瑚色风险强调
- 需要通过渐变、模糊、软阴影、几何形状或轨道感建立氛围，不要只用纯色平铺
- 字体优先使用有性格的显示字体与正文分层，而不是所有标题都回落为普通系统默认感

### 2.5 视觉 Token 使用规则

- 全局颜色、阴影、边框、圆角、焦点态优先从 `apps/desktop/src/renderer/styles.css` 的 `:root` token 读取
- 新增页面不再单独定义浅色或另一套深色变量，除非后续正式支持多主题模式
- 新增卡片优先复用暗色玻璃表面：深蓝半透明背景、细边框、柔和阴影、轻量 `backdrop-filter`
- 主按钮使用青绿到天蓝的克制渐变；次按钮使用深色半透明表面
- 删除、失败、阻塞等危险状态统一使用珊瑚色，不使用高饱和红色
- hover（悬停）只做轻微上浮、边框变亮或阴影增强，不引入大幅位移和复杂动效
- focus-visible（键盘焦点）必须保留清晰轮廓，颜色使用青绿色焦点环

### 2.6 图标系统

- 功能图标统一使用 `lucide-vue-next`，通过 `apps/desktop/src/renderer/src/components/GIcon.vue` 语义组件调用
- 页面代码优先写语义名，例如 `edit`、`delete`、`refresh`、`return`、`copy`，不在模板里直接手写 SVG path
- 图标默认使用线性风格、`currentColor`、16-18px 尺寸和 2px 描边，颜色跟随按钮或状态 token
- 普通图标按钮保持方形触控区，危险操作使用珊瑚色状态，主动作/运行/新增使用青绿色状态
- Provider、模型厂商、产品品牌 Logo 继续使用 `assets/logos/*.svg`，不混入 Lucide 功能图标
- 新增按钮图标时先扩展 `GIcon.vue` 的语义映射，再在业务组件里使用，避免引入第二套图标风格

### 2.7 滚动条系统

- 桌面端所有滚动条默认复用 `apps/desktop/src/renderer/styles.css` 的全局滚动条 token，不在业务模块里重复定义宽度、轨道和边框
- 滚动条保持纤细，无可见轨道边框、按钮边框、上下边框或角落边框；轨道和角落统一透明
- 局部区域如任务清单、应用广场、模型用量、字段级 AI 面板等，只允许通过 `--g-scrollbar-thumb` 和 `--g-scrollbar-thumb-hover` 调整颜色，不单独改变滚动条粗细
- 禁止通过透明 `border` + `background-clip` 制造内缩滚动条，这会导致不同容器出现边框感和粗细不一致

### 2.8 应用级 AI 助手操作条

- 添香小筑、灵绘小筑、瑶音小筑、流光生成台、灵犀对话这类应用级 AI 助手应统一复用 `AiAssistantActionBar.vue`
- 操作条左侧表达当前输出 / 对话 / 生成对象，右侧按“状态图标 + 快速模式 + Gordon 处理”排列
- `快速模式` 表示当前应用的轻量模型生成或专用工具调用，`Gordon 处理` 表示默认 Gordon Agent 主导的深度任务推进；两者不能混用文案或拆成不同位置
- 状态信息优先使用图标按钮和 tooltip 承载，不额外堆一行长状态标签
- 上传、清空、查询结果、写回等辅助动作可保留在各自局部位置，但不替代这条 AI 模式选择操作条

### 2.3 一致性

- 相同类型页面使用相同结构
- 相同语义按钮使用相同位置和样式
- 相同层级标题使用相同字号与间距
- 相同交互切换使用相同页面联动规则

## 3. 页面结构规范

### 3.1 页面两段式结构

列表态页面仍可优先使用上下两段结构：

1. 顶部标题卡片
2. 下方内容卡片

常见适用页面：

- 模型管理
- 任务笔记
- 后续新增的工作台型页面

### 3.2 标题卡片用途

标题卡片只负责：

- 页面名称
- 少量状态信息
- 页面级别的辅助标识

标题卡片不负责：

- 承载复杂操作
- 承载大段说明文案
- 承载编辑行为

### 3.3 编辑页联动规则

当页面从“列表页”进入“编辑页 / 详情页”时：

- 顶部标题卡片需要隐藏
- 页面只保留编辑所需内容区域
- 返回列表后，顶部标题卡片重新显示

这是 Gordon 当前明确确认过的通用规则，后续同类页面默认复用。

### 3.4 单一主工作窗口原则

- 同一个页面层级必须有一个明确主舞台
- 允许存在附着式上下文轨道，例如会话轨道、摘要栏、筛选区，但它们必须从属于主舞台，而不是与主舞台争抢注意力
- 如果既需要列表，又需要编辑或对话，可以继续优先使用“列表态 -> 详情 / 对话态”，但在高频场景下也允许保留轻量侧轨做连续切换
- 辅助信息例如运行上下文、配置摘要、诊断结果，应优先下沉为当前主舞台的局部模块、折叠区、侧轨或消息明细
- 对话类页面可以保留会话轨道，但对话内容仍然必须是视觉主角

### 3.4.1 功能工作区收敛原则

- 对于效率工具、调试工具、日志工具这类“进入后要长时间操作”的页面，首页只承担入口作用
- 首页入口优先使用更小、更克制的 mini 卡片，不把功能详情直接摊平在首页
- 当用户点击某项功能后，应切入该功能的独立工作区，让当前功能内容铺满主容器
- 进入功能后，其它暂时无关的工具、说明卡片和入口广场内容应退出主视窗
- 若需要保留列表、历史记录或模板清单，应将其收敛为轻量侧轨，从属于当前主舞台，而不是与主舞台平分屏幕

### 3.5 对话页默认可用原则

- 对话页默认应可直接输入任务，不把“先配置一堆前置项”作为主流程
- 至少保留一个默认执行角色作为兜底，不让页面进入“无 Agent 不可用”的死状态
- 基础 Skill、基础工具等默认能力应预置到系统里，而不是要求用户先手工搭建
- 非必要配置应收进“高级设置”或局部折叠区，默认保持收起
- 空态页面以一句话引导为主，不堆叠大块说明、教程式卡片或复杂入口

### 3.6 对话页输入区悬浮原则

- 对话页的输入区应固定在聊天窗口底部，以悬浮卡片或固定底栏呈现
- 消息流独立滚动，滚动历史消息时不影响输入区位置和可操作性
- 输入区优先承载当前主动作，辅助设置放在输入区上方或折叠区，不与消息流混排

### 3.7 默认 Agent 表达原则

- 默认 Agent 的身份、模型、工具模式应通过一张轻量信息卡表达，不堆叠多个状态块
- 默认 Agent 能力说明以短句或少量标签呈现，重点说明“能做什么”，不写成长教程
- 常用起手任务可以提供少量快捷提示，但应保持克制，避免把对话页重新做成入口广场

### 3.10 侧向面板原则

- 编辑器、能力表单、配置细项等内容，优先使用侧向滑出面板或附着式编辑层，不必强制跳转为新的整页
- 侧向面板应承接“当前对象的集中编辑”，不承担新的复杂导航
- 面板关闭后，用户应能无损回到原来的主舞台上下文

### 3.8 对话消息结构化展示原则

- 对话输出优先直接在消息体内做结构化呈现，例如标题、列表、引用和代码块
- 代码块应具备清晰的容器边界，并优先提供复制这类贴合开发场景的小动作
- 结构化展示服务于可读性，不额外堆叠说明卡片去重复同一份内容

### 3.9 开发类代码块展示原则

- 面向开发场景的代码块优先提供语言标签、行号和基础高亮，帮助用户快速扫读结构
- diff、命令、配置等高频输出应通过颜色层级区分重点，而不是只依赖纯文本换行
- 代码块增强应保持轻量，不引入喧宾夺主的装饰或过重的阅读负担

## 4. 列表页规范

### 4.1 列表优先

- 对于可管理对象，优先先展示列表，再进入编辑页
- 不要默认直接打开编辑表单
- 列表页应该帮助用户先建立整体认知，再进入单项操作

### 4.2 列表项样式

- 列表项统一使用卡片形式
- 卡片主体用于进入详情或编辑页
- 卡片右侧可以放少量辅助动作
- 卡片上的信息保持简短，只展示关键状态和摘要
- 对于首页入口、工具广场、workflow 列表这类高频入口卡片，默认优先使用横向扁卡，不做高耸竖卡
- 入口卡片不承载大段说明文字；优先保留标题、少量标签、状态和必要数字

### 4.3 排序与数量

- 默认按时间倒序展示
- 若页面存在历史记录，优先展示最近内容
- 当用户已明确要求展示数量时，按约定数量展示，例如“只展示前 5 条”

## 5. 编辑页规范

### 5.1 编辑页抬头

编辑页顶部应尽量简洁，推荐使用三段式结构：

- 左侧：返回列表
- 中间：当前对象标题或日期
- 右侧：保存修改

不建议在编辑页抬头放置：

- 冗余状态标签，例如“编辑中”
- 破坏性操作按钮
- 大段说明文字

### 5.2 标题位置

- 编辑页的核心标题应居中显示
- 对于周报、任务笔记这类日期型对象，日期应作为最核心标题
- 中心标题应稳定，不与其它标签混排

### 5.3 操作收敛

- 编辑页只保留当前操作真正需要的按钮
- 次要动作尽量下沉到局部区域
- 破坏性操作优先移出编辑页，放到列表项或更明确的管理位置

### 5.4 结构化编辑器原则

- 对于周报、任务笔记这类持续更新型内容，优先使用结构化编辑器，而不是退回单一大文本框
- 结构化编辑器优先采用“项目卡片 -> 任务列表”的层级，避免把不同项目混写在同一输入区
- 项目级信息承担阶段结果、风险、备注；任务级信息承担具体动作和状态，不把两者混成一层
- 折叠、状态切换、新增任务等辅助动作应内聚在项目卡片内部，不额外拉出并列侧栏
- 列表页摘要应优先展示项目数、任务数、完成数等结构化信息，而不是只显示“是否有文本”

### 5.5 项目型应用详情页

- 小说、漫画、视频这类项目型应用进入详情后，标题移入左侧可折叠信息轨，顶部标题位优先承接 tab 导航和少量状态标签
- 主编辑区直接铺开当前 tab 的内容，不再额外包一层带标题、字数或状态的外层卡片
- 左侧信息轨的单行输入框、下拉框使用 mini 控件规格，减少垂直内边距和框体高度
- 左侧信息轨字段 label 使用区别于正文的强调色，帮助用户快速扫字段但不增加文字说明

## 6. 破坏性操作规范

### 6.1 删除按钮位置

- 删除按钮不放在编辑页主抬头
- 删除按钮优先放在列表卡片右侧
- 删除操作必须与“进入编辑”操作分离，避免误触

### 6.2 交互要求

- 删除前必须二次确认
- 二次确认、权限申请、失败提醒、风险提醒应使用 Gordon 自绘确认 / 提醒窗口，不使用系统默认 `confirm` / `alert` / `prompt`
- 删除按钮视觉上应弱于主按钮
- 主按钮永远优先表达“保存”“继续”“确认”这类正向动作

## 7. 文案规范

### 7.1 文案风格

- 简短
- 明确
- 不解释过度
- 不重复页面上下文已表达的信息

### 7.2 应避免的文案

- “这里可以……”
- “支持……并且……”
- “工作内容支持手动持续编辑……”
- 大段操作说明或教程式文字

除非用户完成任务必须依赖该说明，否则默认不展示。

### 7.3 保留的文案类型

- 页面标题
- 字段名
- 极短状态提示
- 必要的空态提示
- 明确的按钮文案

## 8. 当前已确认的具体规则

以下规则已经在当前版本中被明确确认，后续新功能默认遵守：

- 首页采用“左侧品牌卡 + 左侧功能卡 + 右侧单一主工作区”的壳层，不再额外保留全宽顶部横栏
- 首页中的模型管理、能力拓展等次要管理入口收进品牌卡局部设置菜单，避免挤占主工作区高度
- 模型管理和任务笔记采用统一的“标题卡片 + 内容卡片”页面骨架
- 首页纵向功能入口卡片可采用左右交错的文案对齐方式，避免连续单侧堆叠
- 列表页显示顶部标题卡片，编辑页隐藏顶部标题卡片
- 列表项点击后进入编辑页，而不是直接内嵌展开复杂表单
- 同一页面层级只保留一个主工作窗口，不并列多个同级功能窗格
- 对话页默认直接可用，前置配置下沉到高级设置
- 对话页消息流与输入区分层，输入区固定悬浮在底部
- 默认 Agent 信息使用轻量身份卡表达，不堆叠多个状态面板
- 对话输出优先在消息体内完成结构化展示，不额外堆叠重复说明卡
- 编辑页抬头优先采用“左返回 / 中标题 / 右保存”
- 返回按钮统一使用小号圆形图标按钮，不再使用圆角矩形外观
- 项目型应用详情页标题进入左侧信息轨，顶部标题位用于 tab 导航，编辑内容不再套二级标题卡
- 周报编辑页的中心标题使用日期
- 周报编辑器优先使用“项目卡片 + 任务列表 + 状态 / 备注”的结构化形态
- 删除动作放在列表卡片右侧，不放编辑页抬头
- 页面避免大量外显说明信息
- 历史记录默认按时间倒序展示

## 9. 新功能开发检查清单

新增桌面端页面前，先自查：

1. 这是列表页、编辑页，还是两者组合？
2. 是否应该复用“顶部标题卡片 + 下方内容卡片”结构？
3. 进入编辑页后，顶部标题卡片是否应隐藏？
4. 当前层级是否只保留了一个主工作窗口？
5. 辅助信息是否已经下沉为局部模块，而不是并列主窗格？
6. 对话页是否默认可用，而不是要求用户先完成前置配置？
7. 页面上是否有不必要的说明文字可以删除？
8. 主按钮、返回按钮、删除按钮的位置是否符合当前规范？
9. 列表项是否保持了简洁信息密度？
10. 破坏性操作是否与主流程操作分离？

## 10. 使用方式

后续新增 UI 功能时：

- 先参考本文件确定页面骨架
- 再参考 `docs/ARCHITECTURE.md` 确认该功能归属层级
- 最后在 `docs/CHANGELOG.md` 记录本次实际落地结果

如果后续对设计风格有新的稳定共识，应优先更新本文件，而不是每次在需求里重复口头描述。
