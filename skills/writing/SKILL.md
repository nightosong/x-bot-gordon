# Writing

用于把小说创作从“直接写一段文本”收敛为可组合的长文本工作流。使用时先判断当前任务属于哪个节点，再按节点输入、输出和上下文依赖完成，不让模型自由漂移。

## 何时使用

| 场景 | 节点 |
|---|---|
| 从题材、主题、风格生成整本书方向 | `story_planner` |
| 重构已有书稿设定、调整主线但需要保留已有资产 | `story_rebuilder` |
| 需要补强时代、地图、制度、组织、规则、势力、怪物或战斗体系 | `world_builder` |
| 需要设计主角、配角、对手、关系与成长线 | `character_designer` |
| 需要判断下一章或下一阶段发生什么 | `plot_engine` |
| 需要先拆本章问题、限制、信息差和代价 | `chapter_planner` |
| 需要把章节简介写成正文 | `chapter_writer` |
| 需要抽取新增事实、伏笔、时间线和规则 | `story_memory`（连续性资料更新） |
| 需要匹配番茄、晋江、轻小说、武侠等风格 | `style_controller` |
| 需要对白、高潮、战斗、反转或爽点强化 | `scene_specialist` |
| 需要按黄金一章/三章检查开篇追读力 | `opening_auditor` |
| 需要检查设定、人名、战力、时间线和伏笔 | `continuity_auditor` |

## 工作流

```text
story_planner
  -> story_rebuilder（已有书稿重构时插入）
  -> world_builder
  -> character_designer
  -> plot_engine
  -> chapter_planner
  -> chapter_writer
  -> style_controller
  -> story_memory
  -> opening_auditor
  -> continuity_auditor
```

## 创作提升准则

这些准则来自长篇奇幻 / 废土 / 冒险类项目的反复修订经验，适用于所有需要提升故事吸引力的小说任务。

### 已有资产重构必须先盘点再融合

重构已有书稿时，不能把 `book.json`、`extraIntroSections`、`storyAssets`、`mapAtlas`、`worldOrganizations`、`monsterSystem`、`combatSystem`、`characterLineage / relationships`、`chapters.json` 整块覆盖成新方向。必须先做资产盘点：

- 必须保留：用户明确要求保留的设定、人物谱系、地图台账、组织关系、怪物体系、战斗体系、伏笔和连续性资料。
- 必须降级：与新方向冲突但仍有价值的旧设定，改成地方传闻、旧名、民间误解、历史残留、黑市行话或后续待定项。
- 可以删除：重复、模板化、已被用户否定、无法服务人物/地图/冲突的空设定。
- 必须同步：若清空章节规划，只能清 `chapters.json` 和章节正文映射；世界设定资产仍要保留或融合，不得随章节一起清空。

重构输出必须明确列出“保留 / 融合 / 降级 / 删除”四类处理结果。若无法确认某项是否该删，默认保留为待审备注。

### 设定必须转化为章节发动机

有逻辑的设定只是起点，不能停在概念解释。每条核心设定都要能转化为：

- 一个角色当下想拿到的目标。
- 一个阻止目标的资源、规则、地理或势力障碍。
- 一个可视化场景或行动难题。
- 一个胜利后的具体收获、代价、敌意或新问题。

如果设定无法推动任务、冲突、选择或后果，应压缩为背景，不要扩写成说明段。

### 浅层刺激和深层反思必须同场出现

长篇不能只靠深刻，也不能只靠热闹。优先让读者先读到浅层刺激：逃生、探险、怪物、交易、追杀、反杀、升级、地图开拓、身份变化；再把深层反思藏进制度、资源分配、命名、价码、阶层、地缘关系和角色选择里。不要用作者议论替代剧情压力。

### 地图先行的长篇规划

涉及大地图、远征、势力边界或奇观探险时，`world_builder` 应优先建立地图台账：

```json
{
  "mapAtlas": {
    "coordinateSystem": {
      "origin": "",
      "unit": "",
      "axes": {},
      "narrativeUse": ""
    },
    "regions": [
      {
        "id": "",
        "name": "",
        "type": "",
        "center": { "x": 0, "y": 0, "z": 0 },
        "bounds": {},
        "coverage": "",
        "features": [],
        "resources": [],
        "monsters": [],
        "factions": [],
        "neighbors": [],
        "geopoliticalRole": "",
        "storyFunction": ""
      }
    ],
    "routes": [],
    "geopoliticalRelations": []
  }
}
```

坐标用于创作规划，不应机械写进正文。正文要写方向、路程感、地貌过渡、势力边界和角色判断。

### 奇观地图必须绑定生态与成长

每处奇观至少需要五项绑定：视觉记忆点、可争夺资源、怪物生态、人类利用方式、主角可带走的成长。奇观不能只是漂亮地名；它必须改变路线、视野、战斗方式、交易规则、资源分布或人物关系。

### 怪物体系必须像生态而不是怪物清单

怪物设计优先参考真实动物体系，再加入奇幻变异。每个怪物群落至少考虑：

- 栖息地和食物来源。
- 繁殖、护崽、迁徙、争水、筑巢、捕猎或共生行为。
- 底层清道 / 滤食者、中层领地 / 迁徙者、上层异常 / 巨型节点 / 类人社会。
- 与人类资源、路线、制度或禁忌的冲突。
- 怪物自己的社会意识、等级、工种、交易或族群目的。

不要把怪物写成只会嘶吼、扑咬、肌肉大、利爪锋利的敌兵。

### 战斗体系必须从生存方式长出来

战斗不是凭空出现的能力对轰。设计战斗体系时，先问这个世界为什么必须战斗：争资源、争路线、争安全区、争社会地位、争命名权、争生存资格。再按职能拆分能力、装备和战术，例如前探、诱导、守路、破甲、医救、斥候、交易、控场、重装、旧械、契约或异化。人和怪物都要符合各自生态与资源逻辑。

### 命名必须有人文来源

保留核心意象即可，不要让所有职业、道具、怪物和地点都套同一个字头。命名应来自历史、地理、职业、俗称、官称、技术名、禁忌名、族群语言或交易称呼。同一事物可因群体不同拥有多个名字。

### 人物谱系先于人物表

长篇人物设计不能只列姓名、身份和性格标签。先建立人物谱系，再补角色档案。谱系的作用是说明一组人物共同承担什么叙事功能，例如：

- 血缘 / 前史线：解释主角性格来源、旧伤、旧物和后置真相。
- 同行 / 伙伴线：测试信任边界、资源交换、救急与背叛。
- 制度 / 城市线：把抽象规则变成人、账册、牌照、债务和权力。
- 对手 / 压制线：建立被低估、被利用、被定价和反夺价码的结构。
- 技术 / 职业线：让战斗体系、旧械、医救、斥候、交易等职能人格化。
- 非人 / 文明线：让怪物社会拥有工种、阶层、交易、禁忌和族群目的。

每个重要角色必须能改变至少一种状态：主角目标、资源、关系、身份、信息差、地图可达性、规则理解或代价。不能只负责夸主角、解释设定、临时送道具或制造一次性情绪。

人物谱系不是可选补充。凡是长篇、游历、多城镇、多组织、多怪物、多阵营或寻亲/复仇/远征结构，必须先建立人物谱系和关键经历，再扩写地图、组织和章节。人物经历要成为串联地图、组织、伏笔和战斗的线，而不是设定完成后的附录。

## 节点约定

### story_planner

输入：`genre`、`theme`、`style`、`length`、作者额外要求。

输出必须结构化：

```json
{
  "premise": "",
  "main_plot": "",
  "core_conflict": "",
  "emotional_promise": "",
  "ending_direction": "",
  "chapter_strategy": ""
}
```

额外要求：

- 必须明确浅层读感承诺和深层主题承诺，避免只写题材标签。
- 必须说明主角成长的可见阶梯：生存、资源、能力、身份、关系或价值选择如何逐步升级。
- 必须把故事介绍写成“为什么读者要继续看”的承诺，而不是世界观百科。

### story_rebuilder

用于已有书稿的方向重构、世界观改造、章节清空前的资产保护、旧设定合并与降级。

开始前必须读取当前 `book.json`、`chapters.json`、已有章节正文清单，并按任务读取 `references/continuity-auditor.md` 以及地图、组织、人物、怪物、战斗相关参考。输出或写回前必须给出：

```json
{
  "preserve": [],
  "merge": [],
  "downgrade": [],
  "delete": [],
  "missing_assets_to_restore": [],
  "next_design_tasks": []
}
```

额外要求：

- 重构主线时，先确定人物谱系和关键经历，再调整世界组织、地图、怪物和战斗。
- 简化世界时，只能降低设定显性程度，不能删除支撑长篇连续性的台账。
- 清空章节规划时，不等于清空世界设定；目录、正文、设定资产分别处理。
- 若用户要求“以丰富世界背景和设定为主”，不得生成章节目录，只维护创作圣经、地图、组织、人物、怪物、战斗、规则和待办。

### world_builder

输出世界规则、资源、禁忌、阶层、势力、代价和冲突源。世界观必须能驱动剧情，不能只列名词。

推荐输出：

```json
{
  "worldview": [],
  "rules": [],
  "factions": [],
  "worldOrganizations": [],
  "mapAtlas": {},
  "monsterSystem": {},
  "combatSystem": {},
  "characterLineage": [],
  "taboos": [],
  "conflict_sources": []
}
```

额外要求：

- 大地图项目必须优先确认地理方位、覆盖范围、相邻区域、路程成本和地缘关系。
- 涉及星球、洲洋、国家、城市、村镇、家宅、建筑或路线设计时，先读 `references/story-map-design.md`。
- 涉及国家、政权、宗门、公司、教会、军队、学院、行会、秘密组织或大型社会制度时，必须先读 `references/world-organization.md`。
- 涉及怪物、异兽、异族、类人怪物、怪物材料或怪物命名时，必须先读 `references/monster-system.md`。
- 涉及战斗体系、能力体系、职业职能、战力成长或人怪 / 人人冲突规则时，必须先读 `references/combat-system.md`。
- 涉及长篇、游历、多势力或寻亲/复仇/远征主线时，必须同步建立人物谱系；世界地图、组织关系、怪物和战斗都要能挂回人物经历。
- 怪物、能力、资源和势力必须绑定具体地貌或社会结构，不要孤立造词。
- 世界冲突应能落到章节任务，例如取水、过桥、进城、守路、交易、撤离、狩猎、证明身份。

### character_designer

输出人物谱系、角色目标、欲望、恐惧、秘密、债务、关系变化和成长弧。角色必须能产生选择成本。

推荐输出：

```json
{
  "characterLineage": [
    {
      "lineage": "",
      "coreCharacters": [],
      "storyFunction": "",
      "pressureOnProtagonist": "",
      "rules": []
    }
  ],
  "characters": [
    {
      "name": "",
      "lineage": "",
      "role": "",
      "narrativeFunction": "",
      "goal": "",
      "fear": "",
      "secret": "",
      "debt": "",
      "resourceOrLeverage": "",
      "firstAppearancePlan": "",
      "relationshipState": "",
      "relationships": [],
      "growth_arc": "",
      "taboos": []
    }
  ]
}
```

额外要求：

- 涉及人物谱系、角色档案、角色关系或长篇多人物规划时，先读 `references/character-lineage.md`。
- 先按谱系组织人物，再扩展单个角色；不要让角色以散点名单方式堆在设定里。
- 每个角色档案必须区分“公开身份、隐秘信息、叙事功能、对主角施加的压力、可回收证据”。
- 角色命名必须有地域、阶层、家族、职业、时代或族群来源，并区分本名、外号、官称、代号、禁忌名和关系称呼。
- 每条谱系至少有一条关系推进规则，例如“有限同行不能突然变成无条件同伴”“制度人物不靠暴躁作恶，而靠平静称量人”。
- 重要角色第一次出场必须带动作任务、资源或冲突，不要用履历介绍开场。
- 如果当前存储结构没有独立 `characterLineage` 字段，可把谱系写入 `storyAssets.relationships / worldview / memoryNotes`，把单人档案写入 `storyAssets.characters`。

### plot_engine

只负责决定下一阶段怎么推进，不直接写正文。

推荐输出：

```json
{
  "next_conflict": "",
  "twist": "",
  "emotion_goal": "",
  "chapter_target": "",
  "character_shift": "",
  "foreshadow_action": ""
}
```

额外要求：

- 每一阶段都要同时推进地图位置、资源状态、敌我关系和主角成长。
- 避免连续使用“观察 -> 遇险 -> 脱困 -> 继续走”的同质节拍；要轮换追逃、夺物、误判、反杀、谈价、交易、探索、规则战和关系撕裂。
- 阶段推进应让故事渐入佳境：新地图带来新规则，新规则逼出新战斗方式，新战斗方式改变主角身份。

### chapter_planner

只负责把当前章节目录和上下文拆成可执行计划，不直接写正文。必须明确本章核心问题、场景顺序、主角目标、阻碍、规则/资源/时间限制、信息差、对手反制、证据载体、代价、人物变化、伏笔/回收和结尾钩子。

推荐输出：

```json
{
  "chapter_problem": "",
  "scene_order": [],
  "constraints": [],
  "information_gap": "",
  "opponent_countermove": "",
  "evidence_carrier": "",
  "cost": "",
  "ending_hook": ""
}
```

额外要求：

- 章节计划必须先回答：本章主角想拿到什么，谁或什么阻止，危险的第二层是什么，赢的证据是什么，代价是什么，为什么下一章必须继续读。
- 若章节有人物出场，必须确认每个出场人物所属谱系、当前关系状态、本章施加的压力和离场后的状态变化。
- 若章节发生在地图型世界，必须确认当前位置、目标位置、相邻路线、控制势力和地貌过渡。
- 若章节出现怪物，必须写出至少一个动物性行为和一个世界观能力行为。

### chapter_writer

只把确定的章节目标写成正文。必须遵守当前章节职责、人物状态、世界规则和风格约束。正文按“问题 -> 规则/资源限制 -> 信息博弈 -> 对手反制 -> 主角选择 -> 代价/新证据 -> 余波或悬念”推进；正文开头不带章节标题。

额外要求：

- 正文优先写具体行动、触感、方位、资源消耗和选择后果，不用抽象形容词替代场景。
- 热血来自明知代价仍做选择，不来自口号；深刻来自制度和资源压力，不来自旁白说理。
- 每章至少让一个状态发生变化：位置、资源、伤势、关系、身份、情报、敌意、规则理解或地图可达性。

### story_memory

章节生成或章节完成后，抽取并更新结构化连续性资料：

```json
{
  "storyAssets": {
    "worldview": [],
    "characters": [],
    "relationships": [],
    "worldOrganizations": [],
    "mapAtlas": {},
    "monsterSystem": {},
    "combatSystem": {},
    "timeline": [],
    "foreshadows": [],
    "rules": [],
    "styleProfile": {},
    "memoryNotes": []
  }
}
```

只记录后续章节必须遵守或可回收的事实，不收录一次性辞藻。`story_memory`、`memoryNotes` 和连续性资料都是内部管理概念，不应被扩写成作品主题、主角能力或世界观机制。

人物资料更新时额外注意：

- 新角色进入主线后必须补 `role / goal / fear / secret / growthArc / relationships / tags / status`。
- 谱系规则优先写入 `relationships` 或 `memoryNotes`，例如“药棚善意必须有账”“下庭怪物会交易而不是只嘶吼”。
- 角色状态变化要可追踪：信任升降、债务新增、秘密暴露、资源损耗、身份改变、阵营摇摆。
- 对死者、失散者、记忆人物、非人角色要明确 `status`，避免后续章节误当普通在场角色使用。

### style_controller

根据目标风格调整叙事密度、句式、声口、爽点、情绪距离和类型期待。风格控制不能破坏既有事实；复杂风格任务先读 `references/style-controller.md`。

### scene_specialist

用于对白、战斗、高潮、打脸、反转、追逃、告白、审判等高张力场景。场面必须有空间调度、信息差、代价和余波；复杂场面先读 `references/scene-specialist.md`。若任务不是单场打斗润色，而是要设计战斗体系、职业能力、战力成长或反制规则，同时读取 `references/combat-system.md`。

### opening_auditor

检查第一章和前三章的商业追读力。开篇首先必须是一个顺畅、具体、能读下去的小故事，再承载世界观、主线伏笔和卖点展示。审核维度包括故事通顺度、主角聚焦度、类型/背景清晰度、卖点或金手指吸引力、追读期待、新颖差异化、信息密度和低级错误风险。必须额外检查六类雷区：开场拥挤、人物过多、群像开局、设定倾倒、环境堆砌、人物白描。输出必须给评分、证据、最小修法和可直接替换片段。

### continuity_auditor

检查人名、关系、动机、时间线、地点、能力边界、世界规则、伏笔账本和视角声口。输出问题必须带最小修复方案；长篇或多章节审核先读 `references/continuity-auditor.md`。

## 输出原则

- 能结构化就结构化，目录、章内计划、连续性资料和审核优先 JSON。
- 生成和修订分离，先完成可推进版本，再把需回头处理的内容写入设定账本。
- 已有书稿重构时，默认增量合并，不默认整块替换；除非用户明确要求删除某类资产，否则先保留并标注为“待审 / 降级 / 暂停使用”。
- 章节规划、章节正文和世界设定是三类资产：清空章节不等于删除设定，调整主线不等于删除地图、组织、人物、怪物和战斗台账。
- 生成类任务先内部自评再输出；只有体检、质检、审核类任务才显式输出评分和问题表。
- 作者约束和 AI 台账分离，作者要求优先；AI 维护的连续性资料只记录事实、信息差、证据载体、伏笔和规则边界。
- 开篇优先单主角、单事件、单视角、单冲突，首场命名人物建议小于等于 3 人；长篇可以群像长线，但不建议群像开局。
- 开篇设定必须剧情化释放，环境描写必须服务事件，人物介绍必须通过行动和选择显形。
- 长篇只看局部上下文会崩线，必须同时参考创作圣经、结构化故事资产、最近章节和后续承接。
- 关键转折必须有证据载体，避免用抽象顿悟替代剧情变化；对手或环境必须反制，避免主角一路顺畅。
- 风格可以变化，事实不能漂移。
- 专业写作助手应描述精准简练，少用“精彩、丰富、宏大、逐渐、命运、真正、某种意义上”等空泛词，除非它们被具体场景、行动或后果支撑。
- 遇到用户批评“无聊、口水化、AI 味、没有吸引力”时，优先回到目标、地图、资源、怪物生态、战斗体系、成长阶梯和章节钩子重构，不只做文风润色。
- 遇到角色单薄、人物散乱或长篇后续难接时，优先建立人物谱系和角色档案：先判断角色属于哪条线、给主角什么压力、改变什么状态，再决定是否需要出场。
- 遇到宏大世界观时，优先把地图、组织、怪物、战斗和人物谱系拆成可互相引用的台账；不要只堆设定名词。
